# LLM 路线答辩讲解点

本文档整理 LLM 意图识别对照路线的三个核心答辩点，供项目答辩/评审使用。

## 一、三种角色（system / user / assistant）在意图识别中的设计

| 角色 | 本次实现中的职责 | 设计要点 |
| --- | --- | --- |
| system | 意图分类任务的完整定义：9 类定义、易混淆类别判定规则、输出格式约束（`src/llm_baseline.py` 的 `build_prompt_v2`） | 分类标准与消歧规则全部收敛在 system 提示词中，保证同一条查询在任何调用场景下判定口径一致；易混淆规则是调优的主战场（见提示词迭代记录） |
| user | 用户的实际查询文本（如"公司上下班时间是几点"） | 保持原始文本，不做改写，避免引入模型偏差；不拼接示例，保证每轮只回答当前查询 |
| assistant | 模型生成的答案：类别编号（0-8） | 温度设为 0 保证确定性；`max_tokens=16` 约束输出长度，只允许返回类别编号，从提示词层面压制解释性输出 |

说明：本任务中 assistant 角色不需要预填示例（few-shot 可以放进 system 或作为 user 历史消息），
两版提示词对比只变更 system 内容，排除其他变量干扰，使准确率差异可归因于提示词本身。

## 二、零样本（LLM）vs 微调（BERT）的取舍

| 维度 | LLM 零样本（deepseek-chat） | BERT 微调（bert-base-chinese） |
| --- | --- | --- |
| 数据需求 | 无需训练数据，只需任务描述 | 需要大规模标注数据（本仓库 20.25 万条） |
| 成本 | 每次调用按 token 计费；200 条 × 2 版约数元 | 一次性训练算力成本（GPU 4 小时级），推理近乎零边际成本 |
| 延迟 | 约 1.3s/条（网络 + 生成） | 毫秒级（本地 GPU 推理） |
| 准确率 | 受提示词质量影响，易混淆类别需显式规则 | 数据驱动，模板数据上可达 99%+ 量级 |
| 长尾/越界 | 语义理解强，对未见表述泛化好；可通过提示词补充规则 | 依赖训练数据覆盖，未见表述易误分 |
| 迭代 | 改提示词即可上线，分钟级 | 需重新训练/微调，小时级 |
| 可解释性 | 判定逻辑可写进提示词，可审计 | 黑盒向量分类，靠混淆矩阵分析 |

取舍结论：数据充足、对延迟和成本敏感的生产场景选微调；冷启动、快速验证、
需要处理开放式长尾表述的场景选 LLM 零样本。

## 三、LLM 路线成本高、延迟高，为什么仍要做这条对照路线

1. **提供性能上限参照**：LLM 的语义理解能力接近"人类判定"，其准确率可作为
   微调模型的上限参照。若 BERT 微调显著低于 LLM 基线，说明数据或训练存在缺陷，
   而非模型能力不足。

2. **覆盖冷启动与长尾**：业务新增意图时，微调路线需要重新标注数据并训练；
   LLM 路线只需更新提示词即可覆盖新类别，是低成本快速响应的兜底通道。

3. **越界/闲聊的鲁棒性对照**：LLM 可以借助提示词中的闲聊边界规则处理
   超出 9 类范围的问题（如"CEO 的工资是多少"），微调路线则依赖置信度阈值。
   两条路线的拒答行为可以互相验证。

4. **答辩的可比性要求**：对照实验需要两条独立技术路线的量化结果，
   LLM 基线提供了"提示词工程"与"数据驱动微调"两种范式的直接对比，
   支撑技术选型的答辩论证。

5. **架构演进兼容**：LLM 路线是未来接入检索增强（RAG）或 Agent 化客服的
   技术基础，保留该路线便于后续架构平滑升级，而非推倒重来。
